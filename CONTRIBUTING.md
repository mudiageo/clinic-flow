## Development Setup

```bash
# Clone the repo
git clone https://github.com/mudiageo/clinic-flow.git
cd clinic-flow

# Install dependencies
pnpm install

# Copy and fill in your environment variables
cp .env.example .env

# Start the dev server
pnpm dev
```

```
clinic-flow/

└── docs/               # Architecture plans, feature plans, and guides
```

## Writing Changes

1. **Branch from `main`** for feature work:
   ```bash
   git checkout -b feat/my-feature
   ```
2. Follow the project rules in `AGENTS.md` — especially:
   - Use `$app/env/private` for server env vars, never `process.env`
   - Use `@lucide/svelte` for icons (not `lucide-svelte`)
   - Never use Dexie directly — use the stores in `$lib/state/`
   - Use SvelteKit remote functions (`query`, `command`) — no `+page.server.ts`
3. Open a **pull request** into `main`.

## Adding a Changeset

Every PR that changes user-facing behaviour (features, bug fixes, performance improvements) **must** include a changeset file. This is what drives automatic version bumps and the CHANGELOG.

```bash
pnpm changeset
```

The CLI will ask you:
1. **Which packages changed?** — select `clinic-flow`
2. **Bump type:**
   - `patch` — bug fix, small improvement (e.g. `0.1.5 → 0.1.6`)
   - `minor` — new feature, non-breaking (e.g. `0.1.5 → 0.2.0`)
   - `major` — breaking change (e.g. `0.1.5 → 1.0.0`)
3. **Summary** — a short description of the change (see format below)

This creates a Markdown file in `.changeset/`. **Commit this file with your PR.**

> ℹ️ Pure documentation, chore, or CI-only PRs do not need a changeset.

## Changeset Message Format

Follow the same format used in the [omni-svelte](https://github.com/mudiageo/omni-svelte) project:

```
- {summary} {ref}
```

The `{ref}` is automatically injected by `@changesets/changelog-github` as a PR link.

### Summary conventions

Use a **conventional commit-style prefix** in the summary:

| Prefix | When to use |
|---|---|
| `feat(scope):` | New feature |
| `fix(scope):` | Bug fix |
| `perf(scope):` | Performance improvement |
| `chore:` | Maintenance, dependency bumps |
| `docs:` | Documentation only |
| `refactor(scope):` | Code refactor with no behaviour change |

**Examples:**

```
feat(ai): add SOAP Note generator with clinical safety guardrails
fix(queue): prevent AI risk score from downgrading existing triage level
perf(sync): batch Dexie writes to reduce IndexedDB round-trips
feat(pharmacy): implement RxBrain drug interaction safety checker
fix(marketing): correct broken links on /support index page
```

### What makes a good summary?

✅ `feat(triage): add AI risk score badge with hover rationale tooltip to queue cards`  
❌ `update queue card` — too vague  
❌ `Fixed stuff` — not descriptive

## Release Channels

| Channel | Branch | Tag pattern | Intended for |
|---|---|---|---|
| **stable** | `main` | `v1.0.0` | Production PHC deployment |
| **beta** | `beta` | `v1.0.0-beta.3` | Supervised testing only |
| **alpha** | `alpha` | `v1.0.0-alpha.1` | Internal preview builds |
| **nightly** | `nightly` (cron) | `v1.0.0-nightly.20260914` | Automated overnight snapshots |

> ⚠️ **Clinical Safety Note:** Only `stable` builds should ever be deployed in a live Primary Health Centre. Pre-release builds may contain untested AI features and schema migrations that are incompatible with existing patient data.

## Release Pipeline (CI/CD)

The release pipeline is fully automated using [Changesets](https://github.com/changesets/changesets) v3.

### How it works

```
Developer merges PR with a .changeset file
         │
         ▼
.github/workflows/release.yml detects changesets on main
         │
         ▼
Changesets bot opens a "chore: version packages" PR
  - Bumps package.json version
  - Writes entries to CHANGELOG.md
  - Deletes consumed .changeset/*.md files
         │
         ▼
Lead developer reviews and merges the Version PR
         │
         ▼
release.yml detects that the version PR was merged
  - Creates a GitHub Release with the new tag
  - Dispatches build.yml
         │
         ▼
build.yml runs cross-platform Tauri builds:
  - Windows (x64) → .exe
  - macOS (Apple Silicon) → .dmg
  - macOS (Intel) → .dmg
  - Linux AMD64 → .deb
  - Linux ARM64 → .deb
  - Android (arm64, armv7, x86_64) → .apk
         │
         ▼
Artifacts uploaded to GitHub Release assets
/download page immediately reflects new version
```

### Key scripts

```bash
pnpm changeset        # Add a changeset to your PR
pnpm version          # Consume changesets → bump version + update CHANGELOG (run by CI)
pnpm release          # Publish (run by CI after version PR merges)
```

## Pre-release Workflow (Beta / Alpha)

### Entering pre-release mode

```bash
# Switch to the beta branch
git checkout beta

# Enter pre-release mode (only needs to be done once per cycle)
pnpm changeset pre enter beta

# Add changesets as normal
pnpm changeset

# Version bump — creates v0.2.0-beta.1, v0.2.0-beta.2, etc.
pnpm version
git add . && git commit -m "chore: version packages (beta)"
git push
```

### Exiting pre-release mode (graduating to stable)

```bash
# Exit pre-release — back to stable versioning
pnpm release:exit-pre
git add . && git commit -m "chore: exit beta pre-release"

# Merge beta into main and let the normal release pipeline publish stable
git checkout main
git merge beta
git push
```

## Nightly Builds

Nightly builds are created **automatically at 00:00 UTC every night** via `.github/workflows/nightly.yml`.

- Tag format: `v{version}-nightly.{YYYYMMDD}` (e.g. `v0.2.0-nightly.20260914`)
- Marked as **pre-release** on GitHub
- Shown in the `/download` page under "Pre-release Channels"
- You can also trigger a nightly manually via the **Actions → Nightly Build → Run workflow** button on GitHub

> Nightly builds are never automatically deployed. They must be explicitly downloaded and installed.

## Manual Tauri Build

To trigger a build manually for any specific tag or channel:

1. Go to **GitHub → Actions → Tauri Build Workflow**
2. Click **Run workflow**
3. Fill in:
   - `tag` — e.g. `v0.2.0-beta.1`
   - `prerelease` — `true` or `false`
   - `release_name` — optional override (e.g. `ClinicFlow Beta Preview`)

The workflow will automatically detect the channel from the tag name and set the GitHub Release `prerelease` flag accordingly.
